# 测试用例

## TC-01：环境连通性验证

**目的**：验证 WPS 连接与 MCP 服务可用

**步骤**：
1. 启动 WPS Writer
2. 确认 OpenCode WPS 插件已显示侧边栏
3. 执行 `wps_office_list_apps` 确认 MCP 连通
4. 创建空白文档

**期望**：所有步骤成功，MCP 响应正常


## TC-02：Layer 1 规则引擎基础验收

**目的**：验证 7 条新规则的检出准确性

**步骤**：
1. 创建测试文档，逐条插入 F01–F10（句式杂糅 10 条）
2. 运行 `proofreadBasic`
3. 记录每条句式的检出状态
4. 创建测试文档，逐条插入 C01–C10（冗余词 10 条）
5. 运行 `proofreadBasic`
6. 记录每条冗余词的检出状态
7. 断言每条 issue 的 `metric` 字段正确

**期望**：
- 句式杂糅：≥ 8/10 检出（F01/F02/F04/F06/F07 正则命中率最高）
- 冗余词：≥ 12/15 检出
- metric 字段非空且值正确

## TC-07：P12 完整周期校验

**目的**：验证 `proofreadBasic` → `confirmProofread` → 修复 的完整周期

**场景**：
1. 创建文档含"通过这次学习使我受益匪浅"
2. 启动校对流程 `proofreadBasic`
3. **场景 7a（未 proofread）**：直接调用 `replaceInParagraph` → 应被 P12 拦截
4. **场景 7b（未 confirm）**：proofreadBasic 后直接修复 → 应被 P12 拦截
5. **场景 7c（未修复）**：proofreadBasic → confirm → 直接结束 → 应被 P12 拦截
6. **场景 7d（完整周期）**：proofreadBasic → confirmProofread → replaceInParagraph → 放行

**期望**：7a/7b/7c 被拦截，7d 放行


## TC-08：P13 修复长度校验

**目的**：验证修复文本长度限制

**场景**：
1. 创建文档含"通过这次学习使我受益匪浅"（原文长度~10字）
2. **场景 8a（正常）**：修复为"这次学习使我受益匪浅"（长度接近）→ 放行
3. **场景 8b（超限）**：修复为超长文本 → 应被 P13 拦截

**期望**：8a 放行，8b 拦截


## TC-09：P14 基础校对校验

**目的**：验证基础校对不能跳过

**场景**：
1. 创建文档含问题句
2. **场景 9a（跳过）**：跳过 proofreadBasic 直接 confirm + 修复 → 应被 P14 拦截
3. **场景 9b（正常）**：proofreadBasic → confirm → 修复 → 放行

**期望**：9a 拦截，9b 放行


## TC-10：P15 修复数量边界（含 `_force_ai_fix`）

**目的**：验证基础校对无问题时的修复数量限制

**场景**：
1. 创建"干净"文档（proofreadBasic 返回 0 个 issue）
2. **场景 10a（修 1 处）**：AI 修复 1 处 → 放行（免费额度）
3. **场景 10b（修 2 处无 flag）**：AI 修复 2 处无 `_force_ai_fix` → 应被 P15 拦截
4. **场景 10c（修 2 处有 flag）**：AI 修复 2 处且传 `_force_ai_fix: true` → 放行

**期望**：10a 放行，10b 拦截，10c 放行


## TC-11：P16 交叉校验（含 `_force_ai_fix`）

**目的**：验证 `findText` 与已知 issue 的交叉校验

**场景**：
1. 创建文档含"通过这次学习使"（Layer 1 检出，original="通过这次学习使"）
2. **场景 11a（匹配）**：AI 修复 `findText="学习使"`（子串匹配 original）→ 放行
3. **场景 11b（不匹配无 flag）**：AI 修复 `findText="完全不相干"` → 应被 P16 拦截
4. **场景 11c（不匹配有 flag）**：AI 修复 `findText="完全不相干"` + `_force_ai_fix: true` → 放行

**期望**：11a 放行，11b 拦截，11c 放行


## TC-12：修订数一致性验证

**目的**：验证实际修订数 = 决策引擎决策的 autoFix 数量

**步骤**：
1. 校对完成后，从报告统计中获取 autoFix 总数
2. 与 WPS COM `GetRevisionsCount` 对比
3. 断言一致

**期望**：autoFix 总数 = 实际修订数


## TC-13：校对报告统计正确性

**目的**：验证五维评分报告按 metric 分组统计正确

**步骤**：
1. 完成全文校对
2. 调用 `generateProofreadReport`
3. 检查报告结构：
   - 按 metric 分组表格（fluency / conciseness 各自检出数、修复数、仅报告数）
   - 优化建议（未自动修复）小节带分数列
   - 统计摘要

**期望**：
- 分组统计数字与逐条跟踪表一致
- 优化建议条目全部来自 6–8 分 / 10–25% 冗余区间
- 优化建议每条带分数列
