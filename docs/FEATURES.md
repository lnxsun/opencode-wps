# 特色功能详解

本文档详细介绍 OpenCode WPS 的两大特色功能：**文档填写（模板自动填值）** 与 **大文档校对（铁律 3.0）**。

> 📖 日常使用方式（打开面板/对话操作/Agents 调用）见 [USAGE.md](https://cnb.cool/lnxsun/opencode-wps/-/blob/main/docs/USAGE.md)。

## 文档填写 — 模板自动化填值

根据预定义的字段映射，自动从结构化数据源（JSON/Excel/数据库）中提取值，精准填充到 Word 文档模板的指定位置，全程开启修订模式，确保填值过程可追溯。

### 工作流程

1. **评估文档** — `getActiveDocument` 获取文档总段落数与结构，输出分批计划（T1）
2. **分批拉取** — `getDocumentParagraphs` 分批次获取段落（每批 ≤200 段，T2/T5）
3. **定义字段** — `findInDocument` / `getBookmarks` 定位模板字段名称和位置
4. **映射数据** — `smartFillField` 将数据源字段值与模板字段对应（支持 auto/underline/afterColon/afterLabel/placeholder 五种模式，T6/T7/T8/T9）
5. **预览校验** — 自动检测字段格式（日期/金额/编号等），首次填写前输出「文档字段 ↔ 用户值」对照表并获用户确认（T7）
6. **批量填值** — 分批次（每批 ≤200 段）调用 `smartFillField` / `replaceBookmarkContent` 执行填充（填写前已开启修订模式 T3），所有填值自动加下划线（T11），禁止编造数据，跳过签字/印章等不可自动填写的字段（T8）
7. **查漏复核** — 填写后调用 `findInDocument` 检查遗漏（T4）

### 治理规则（T1-T11）

| 规则 | 说明 |
|------|------|
| T1 | 填写前调用 `getActiveDocument` 评估文档规模，确定段落总数和字段位置 |
| T2 | 填写前调用 `getDocumentParagraphs` 分批，每批 ≤200 段 |
| T3 | 填写前调用 `enableTrackChanges(true)` 开启修订模式 |
| T4 | 填写后建议调用 `findInDocument` 检查遗漏 |
| T5 | 批次连续性检查（同 P2） |
| T6 | 禁止子串重复填写（新 keyword 是已填 keyword 的子串/超串时拦截） |
| T7 | 禁止编造——首次填写前必须输出「文档字段 ↔ 用户值」对照表并获用户确认 |
| T8 | 跳过签字字段（含「签字/签名/签章」的关键字无需填写） |
| T9 | 日期字段推荐 underline 模式 |
| T10 | 禁止同一 (keyword, value) 重复填写 |
| T11 | 所有填入的值必须加下划线（`smartFillField` 工具层自动执行） |

### 适用场景

- 合同/协议批量生成（将订单数据填入合同模板）
- 报告/报表自动生成（将统计数据填入报告模板）
- 公文/信函批量制作（将收件人信息填入信函模板）
- 审批表单填写（将审批结果填入审批单模板）

## 大文档校对 — 铁律 3.0 严格逐批校对

基于 `proofreadBasic` 工具的严格逐批校对流程，引入**铁律 3.0** — 禁止 AI 跳过基础校对、禁止跳过确认直接修改、禁止 AI 编造修复内容。通过治理层 P 规则（**P1～P4 四条**，以 `.opencode/plugins/governance.js` 源码为准）在代码层强制执行。

### 校对流程

1. **评估文档** — `getActiveDocument` 获取文档总段落数，输出分批校对计划（P2 前置要求）
2. **生成批计划** — `getDocumentParagraphs` 获取本批段落（**每批固定 200 段**，从第 1 段起连续分批；开始时按 200 段规划好总批次数，然后严格一批一批推进直至结束，**严禁中途改大批量或一次跑多批**）。
   - **为何控制单批大小**：单批过大易使 MCP 输出被截断导致漏检；**单批固定 200 段**（跨运行时单一来源 `PROOFREAD_BATCH_MAX`），文本随批走。超长（或含 `\f` 等控制字符）时落盘后走 `file_path`（UTF-8）。
   - **例外**：超大型文档靠后批次反复超时，经向用户说明后可将该批临时缩减为更小批量继续推进（见 SKILL.md「getDocumentParagraphs 超时怎么办」），严禁跳过或伪造进度。
3. **逐批校对** — `proofreadBasic` 每批独立调用，AI 逐批检查
4. **确认修复** — `confirmBatchAiProofread` 确认本批问题（必须先调 `proofreadBasic`）
5. **执行修复** — `replaceInParagraph` 修复本批问题 → **进入下一批**（本批未完成禁止下一批）

### 铁律 3.0 核心规则（4 条）

> ⚠️ **条数与判据的唯一事实源是** [`.opencode/plugins/governance.js`](https://cnb.cool/lnxsun/opencode-wps/-/blob/main/.opencode/plugins/governance.js)。
> 治理层只保留「**服务端不具备的独立信息**」的校验：同一不变量在治理层与服务端各写一遍，
> 只会产生「两层状态不同步」（AI 卡死或误拦），这是校对线历史 Issue 的根因。
> 因此收敛方向上不变量按「一条规则 = 一个环节」归并，删一条不再需要「证明服务端已覆盖」。

| 规则 | 环节 | 说明 |
|------|------|------|
| **P1** | 批次推进前置 | 首次 `getDocumentParagraphs` 必须从第 1 段开始、单次 ≤200 段、批次必须连续；当前批未走完（`proofreadBasic` → `confirmBatchAiProofread` → 有问题则 `replaceInParagraph`）不得获取下一批；`confirmBatchAiProofread` 必须在 `proofreadBasic` 之后。**例外（Issue #420）**：请求区间完全落在「本批已取过区间」内（`end ≤ 上批逻辑末段`）的**只读重读**放行 —— 取段不推进进度、不可能跳过内容，原判据会把它与「推进下一批」一并拦死 |
| **P2** | 替换/收尾前置 | 任何替换前必须先 `enableTrackChanges(true)`；分批流程禁用 `findReplace`；`proofreadAccumulate` 首次必须先经 `getDocumentParagraphs` 取段落、`getDocumentTextByRange` 只拉本批范围、单次 `proofreadBasic` 只传本批文本；覆盖全文后禁止继续推进，必须 `generateProofreadReport` 收尾（**仅在「本批已上报」后生效**：单批 ≤200 段文档首批取段即覆盖全文，不得因此把本批的取文本/校对/替换全拦死——Issue #395 RC-2）；禁止 AI 手动 `write` 伪造报告 |
| **P3** | 替换内容校验 | `replaceInParagraph` 的 `findText` 必须精确匹配已知 issue 的**完整原文**（不得含截断标记 `...`/`…`），且必须在所属段落内**唯一**（不得用子串、2 空格、单字）；确需强制修复传 `_force_ai_fix: true` |
| **P4** | 进度真实性 | 上报进度不得超「本批实际取回末段」（服务端不知道取回了哪几段，属治理层独立信息）；上报的 issue 段落索引必须落在本批实际窗口内，禁止复用陈旧 issue 填充 |

> **已下沉服务端（治理层不再重复）**：进度严格递增 / 单批增量 ≤200 / 覆盖门禁 / 首次缺 `doc_info`
> —— 由 `proofreadAccumulate` / `generateProofreadReport` 强制；
> 治理层只保留服务端**看不到**的真值（`batchActualStart/EndParaIndex`、`paragraphTexts`）。
> （**已删除**：批次表与步骤凭证、会话磁盘落盘/重启恢复 —— 见 `proofread-types.ts` 内的机制说明。）

### 校对报告防伪造（Issue #116 session_ffa8 问题一）

校对报告**必须由服务端 `generateProofreadReport` 基于真实累计的校对数据生成**。真实会话中 AI 在 `generateProofreadReport` 失败后直接 `writeFile` 手动拼 Markdown 报告（3 份数据互相矛盾），绕过了服务端真实数据。治理插件 **P2** 在写「校对报告」路径时若服务端未成功生成报告即拦截；SKILL 铁律 5 明确禁止手动伪造。

### 禁止重复获取已处理段落（Issue #116 session_ffa8 问题四）

真实会话中 AI 已处理完某批次后，又对已检查过的段落执行 `getDocumentParagraphs(start=1)` 回卷重复扫描，既浪费 token 又可能造成重复/遗漏的修复误判。治理插件 **P1** 记录上一批结束段落号 `N`，当已处理到 N 段后再次从段落 1 回卷获取（`start=1`）时直接拦截，要求批次必须严格连续向前推进。如需重新开始，请调用 `getActiveDocument` 并传 `_restart: true` 显式重置进度（CR R2-1：同一文档重复刷新 `getActiveDocument` 不打断已处理批次；仅当显式传 `_restart: true` 或切换到不同文档时才重置）。

### 分批校对执行稳定性整改（Issue #229）

真实会话中分批校对「不能按分批从头到尾严格执行」，根因集中在**批次中途失败死锁、输出截断导致状态错乱、JSON 解析失败致规则失灵、多文档状态互相污染、总段数解析失败**五类。治理层逐一整改（PR #230）：

| 根因 | 整改 | 规则/位置 |
|------|------|-----------|
| **批次中途失败死锁**：本批 `proofreadBasic` 连续失败时无法重试同批、也无法取下一批/回卷，唯一出路是重置全部进度 | **同批重试放行**：请求范围与本批实际范围一致时放行重新获取段落（不再被 P1 当"回卷/不连续/未完成"拦截）；但**跨批推进仍要求本批走完** `proofreadBasic → confirmBatchAiProofread → replaceInParagraph` 完整链条 | P1 |
| **输出截断导致状态错乱**：治理层信任截断后的输出，把末段 index/end 当本批边界，导致段落被静默漏检 | **批次边界以请求参数为准**：以请求的 `end_paragraph` 作为本批逻辑结束，不信任输出截断处；同时记录**实际返回**的首/末段供 P4 进度真实性判定 | after hook |
| **proofreadBasic JSON 解析失败**：返回截断致 `extractJsonFromOutput` 返回 null，无问题限流与交叉校验误判"无问题"或失效 | **三态化**：解析失败按"未知"（`null`）处理，无问题限流与交叉校验均放行，避免合法修复被误拦截 | `proofreadHadIssues` |
| **会话状态作用域过宽**：状态按 OpenCode 会话 ID 存储，同一对话校多文档互相污染 | **按文档隔离**：跟踪 `activeDocPath`，文档切换自动完整重置全部批次状态；同一文档重复 `getActiveDocument` 不打断进度（无容量上限与 LRU 淘汰） | `getSessionState` |
| **总段数解析失败**：`getActiveDocument` 走 launcher 回退输出"总段数: 未知"，正则不匹配致 `totalParagraphs=0`，收尾报告完整性门禁失效 | **兜底提取**：从 `getDocumentParagraphs` 输出的"共 N 段"兜底提取文档总段数，确保覆盖全文判定与报告门禁可用 | after hook（问题5） |

**重新开始语义**：同一文档内**刷新 `getActiveDocument` 不重置进度**（避免打断已处理批次）。如需在同一文档内显式重新开始整个校对（覆盖全文后重跑、报告失败后重来），请在 `getActiveDocument` 中传 `_restart: true` 完整重置批次进度；切换到不同文档则自动重置。

### 校对报告可信度整改（Issue #277）

基于真实校对会话（#247 复盘诊断，5000+ 段）暴露的**报告失真与规则误报**，整改 3 个 P1 + 2 个 P2：

| 编号 | 问题 | 根因 | 整改 |
|------|------|------|------|
| **P1-1** | 33 处「仅报告未修」被报告标为「全部已修复 ✅」 | 报告门禁 `_coverageComplete` 只看**段落覆盖**，未校验每条 issue 的修复归因 | `ProofreadIssueEntry` 新增 `fix_action`（`fix` / `report_only`）；`normalizeIssueFixAction` 归一化变体（`report-only` / `REPORT ONLY` / 驼峰 `fixAction`），读取侧 `isReportOnly(issue)` 统一判定（对磁盘恢复的裸 session 同样有效）；门禁拆为 `_coverageComplete && _allFixed` 双判据；R6-1 补齐最后一处通道——**「AI 漏传 `fix_action`」**会被归一化静默兜底成 `fix`（保守语义），故新增 `fix_action_inferred` 标记，报告附「口径说明」如实披露「修复归因来自服务端推断，非客观核实」，在**不误伤历史会话**的前提下关闭「漏传 = 已修」的剩余通道 |
| **P1-2** | 中英混排大面误报（`，D1`、`负责方A，`、`QPS，目录`、`。SLA`） | 旧正则 `[a-zA-Z]+[，]` 只见「字母 + 全角标点」即判混排，把中文句中代号/缩写当英文词 | 仅当标点左侧是**被西文边界包围的西文词**才命中（R7-1 修正为与位置无关）；单字母代号、CJK 紧邻缩写、以及「中文 + 空格/缩进 + 缩写」（`使用 QPS，目录`）一律不命中 |
| **P1-3** | 的地混淆误报（`不一致的成果` → `一致地成果`） | 命中 `一致的` 即替换，不看「的」后接名词还是动词 | 「的」后必须紧接**动词性成分**（执行/处理/进行…）才替换；后接名词（成果/目标/结论）不报 |
| **P2** | 报告口径自相矛盾：`问题数 × 2 = 17` 而问题数为 34 | 文案词序颠倒 | 改为「修订数 ÷ 2 ≈ 替换类问题数」；**校验基准统一为「声称已修」问题数**（R1-3 起，R10-1 收口），交叉校验段与 TC-12 口径说明段**同基准**——此前两段一用「声称已修」一用「全部问题数」，同一份报告里一段声明「仅报告未修不参与校验」、另一段又把它的存在当「对不上」的原因（自相矛盾）；不整除 / 不一致 / 全为 report_only 三种情形分别如实说明 |

**规则维护契约（写给后续维护者/AI，勿删）**：

- **的地混淆 / 的得混淆的判定以「的」后是否为谓语成分为准**——后接名词中心语（`不一致的成果` / `最大的好处`）一律不报。这是 P1-3 与 R4-1 的共同结论。
- **白名单不得纳入词性元词**（`形容词` / `动词` / `副词` / `名词`…）：它们是规格描述用词，与现实待纠错词同形，纳表必生误报（R1-1 已实证）。
- **名动同形词（`说`/`看`/`干`…）不得加入白名单**，交 Layer 2 AI 语义层判定。
- **取舍原则**：宁可少报（假阴性）不可误报（假阳性）——误报会诱导 AI 把正确文本改坏。
- 新增/修改规则词必须**同时补正例（能命中）与负例（不得命中）各至少 1 条**。

### 同族校对规则边界收敛（Issue #277-C / PR #291）

真实会话（#277）暴露**同族规则边界缺失**——同一族规则（`变的/做的`、`在(次|来|去)`、`通过(A)(使|让|令)`）在部分语境下把**正确写法**误判为错别字，规则层持续产出误报。本次按「右边界守卫」同构方案收敛：

| 编号 | 问题 | 根因 | 整改 |
|------|------|------|------|
| **C1-1** | 句式杂糅跨句乱吃：`通过(.*?)(使\|让\|令)` 的 `(.*?)` 无长度/句读约束，会话实证 3 条误报、**最长匹配 124 字符**，AI 按 `original` 定位替换即成整段污染 | `A` 无上界——「通过A使B」的 A 是**紧凑动宾短语**（真例 A=4 字），不会跨句跨段 | `A` 限定「不含句末标点/换行、≤8 字」：`/通过([^。；！？\n]{1,8}?)([使让令])/g` |
| **C1-2** | `使用` 被误排除：`通过A使用B` 是正常动宾，需排除；但 `使 + 用X`（真杂糅，如 `使用户体验`）与 `使用X` **字符层面完全同形** | 初版用「否定 `用` 字」→ 误吞 `使用户`（真杂糅）；加入单字 `人` → 误吞 `使用人员`；泛化名词白名单（30 项）→ 8 项会吞真杂糅（**修一个冒一个**） | 改为**强搭配白名单**（12 项：`意见/时长/说明/情况/方式/方法/范围/权限/记录/文档/系统/环境`）+ **必须满足词界**（表项后接 CJK 视为新词，`记录员`/`文档化` 不豁免）；单字 `人` 明确不入表 |
| **C1-3** | `变的/做的` 误报：「总额不变的前提下」被当成「变得」的得混淆（会话实证：段落 635） | 裸规则 `变的` 无条件替换，不看「的」后接名词还是动词 | 新增**右边界守卫** `isRightBoundaryOk`（与 `isWesternSegment` 左边界互补）；判据为**左语境 + 右词性联合**：左侧紧邻非 CJK（串首/空白/ASCII 标点）+ 右侧名词性 → 丢弃；左右皆 CJK（`数值变的很少`）→ 一律仍报 |
| **C1-4** | 左语境判据取错：R1 初版「只按右侧前缀匹配」，白名单含 `数据/结果/状态` 等可作**主语**的名词，把 `数值变的很少` 的「数值」误判为「不变的」结构而**丢弃真修复** | 判定必须锚定「变」字**紧邻的左邻字**（`text[index-1]`，`index`=「变」在文中的下标）而非只看右侧前缀 | 新增 `isLeftContextCjk`：左邻为汉字且该字**不属于**「否定/变更词」集合（`不/未/没/要/有/会/能/可/变/已`）时，视为「主语 + 变的」谓语语境，不允许白名单豁免（判据以源码为准，见 `proofread-rules.ts` `isLeftContextCjk`；**注意**：读的是「变」左侧**单字**，非「前 3 字」） |
| **C1-5** | `在次` 时间名词误报：「月账单在**次月**10日前确认」被当成 `在次⇒再次`（会话实证：段落 3950） | 「介词 在 + 时间名词 次月」与「再次」的误写**同形**；豁免面需精确锚定 | 仅 `在次` 分支豁免标准时间名词（`次月/次日/次周/次年`）；**`在来`/`在去` 分支不豁免**（保持原行为，正确用法如「在去年完成」属历史误报，交 Layer 2 / 另案）；收窄过程：通用量词 → `月/日/周/年/季` → 去 `季`（`次季度` 会漏报真错）→ 仅 `次` 分支 |

### 同族规则边界收敛补完（Issue #295 / PR #301）

#277-C 只收敛了 `通过A使B`，**同族另两条 `.*?` 无界规则未跟上**（历史遗留）：

| 编号 | 问题 | 根因 | 整改 |
|------|------|------|------|
| **F2-1** | `根据(.*?)(显示\|表明\|证实)` 跨句乱吃（实测命中 62 字符，跨过「。」吃到下一句） | `A` 无长度/句读约束，与 C1-1 同类缺陷 | `A` 限定「不含句末标点/换行、≤12 字」：`根据((?:(?![.!?]\s)[^。；！？\n\r\v\f\u2028\u2029]){1,12}?)(显示\|表明\|证实)`。上界 12 字由实测夹逼（正例最长 `第三方检测机构检验报告`=12 / 负例 A≥22），**不得照搬 C1-1 的 8 字** |

**验证**：净增 25 条单测（106→131，`proofread-rules.test.ts`），QA 独立对照实验（基线 main 106/106 vs 本次 131/131，无本次改动导致的失败）、`tsc` 0 错、`preflight` EXIT=0；性能 78K 字符 8ms（负向断言无回溯灾难）。评审-修复 R1–R10 共 10 轮清零。

**规则维护契约（Issue #295 增补，勿删）**：

- **同族规则的上界必须逐条实测夹逼，不得相互照搬**（F2-1：`根据` 需 12 字，照搬 `通过` 的 8 字会漏报真杂糅）。

- **换行符集必须显式全列，不得用 `\s` 简写**（F2-4：`\s` 含空格会误伤 A 内合法空格）。
- **归一化钩子必须保证「只允许尾部修剪」**（F2-5：仅查长度会放行异串，破坏 `offset` 一致性）。

**规则维护契约（Issue #277-C 增补，勿删）**：

### 治理机制（hooks 闭环）

```
before 钩子拦截违规 → 工具执行 → after 钩子更新状态 → before 钩子校验状态
```

- `proofreadHadIssues`：记录基础校对是否发现问题 → P3 据此限制 AI 自定修复次数
- `proofreadIssueOriginals[]` / `paragraphTexts`：存储基础校对返回的 issue 原文与本批段落原文 → P3 交叉校验与段内唯一性判定
- `proofreadCalledThisBatch` / `aiProofreadDoneThisBatch`：标记本批校对与确认状态 → P1/P2 共用
- `replaceCountThisBatch`：本批替换次数计数 → P3 超限拦截
- `batchActualStart/EndParaIndex`：本批**实际返回**的首/末段 → P4 进度真实性与窗口校验

### 疑似问题（待确认问题）机制（Issue #116）

校对过程中，AI 常识别出**疑似但未确认**的问题（如语义存疑、疑似误写、需人工核实的计算错误等）。此前这些疑似问题只能留在 AI 上下文中，会话压缩后即丢失。

新增 `suspected_issues` 参数（`proofreadAccumulate` 支持）：

- AI 可将**未确认的问题**单独累加到 `suspected_issues`（而非 `issues`）
- 报告中单独列出「⚠️ 待确认问题」节，标注「未修改，请人工核对」
- **不纳入六维评分**，仅作提示，避免误报影响报告可信度
- 即使没有确认问题（`issues` 为空），只要存在疑似问题，报告仍列出该节
